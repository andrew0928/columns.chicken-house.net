# 當 Coding Agent 能寫 code，架構師的價值就從「實作產出」轉向「規格收斂、驗證條件與系統建模」

前幾天聊 Agent MVP 做法時，我心裡真正想談的其實不是「某個工具好不好用」，而是另一個更根本的問題：

**AI 的進步，工作流程應該要有根本上的改變才對。那麼架構師（或資深技術人員）本身該做什麼調整？**

這幾年很多人會引用 Kent Beck 那句話：

> “The value of 90% of my skills just dropped to $0. The leverage for the remaining 10% went up 1000x. I need to recalibrate.”

翻成白話大概是：

> AI 讓我 90% 的技能價值快速下降，但剩下 10% 的價值被放大了 1000 倍，所以我必須重新校準。

這句話我一直覺得很有道理，但如果你沒有真的弄清楚那個 **10% 到底是什麼**，也沒有真的調整自己的工作方法，那它就很容易只剩下心靈雞湯。

我這篇想談的，就是我這段時間實作下來的一個答案：
**AI 時代，架構師的價值更集中在處理不確定性、收斂規格、設計驗證條件、建立系統模型，以及定義讓 Agent 能持續運作的條件。**

---

## 架構師的 10%，其實是「主動成為瓶頸」

如果用限制理論（Theory of Constraints）的角度來看，整個系統效率取決於瓶頸。換句話說，當 AI 大量接手可被標準化、可被加速的工程工作時，對架構師而言，真正高價值的做法反而是：

**主動讓自己成為那個關鍵瓶頸。**

這裡說的「瓶頸」不是拖慢團隊，而是你把時間和精力集中在那些 **非你不可**、而且會影響整體結果的環節。這些通常不是「多寫幾千行 code」，而是：

* 問題拆解與建模
* 需求與規格收斂
* 驗證條件設計（Done Criteria）
* 模組邊界與跨系統介面定義
* 跨團隊溝通與風險前置消化

我後來重新回頭看這兩年 AI 對軟體開發的改變，越來越確定：
**AI 強的是加速「確定性任務」，而人的價值會更集中在處理「不確定性」。**

---

## 架構師的核心任務沒有變，但工作方法變了

我對架構師工作的理解一直沒有變太多：本質上還是要理解商業需求與技術要求，替產品與決策者翻譯需求，再把它轉成開發團隊能執行的做法（規格）。

但在 AI 時代，我會把整個流程更明確地拆成兩段：

### ① 處理不確定性的問題

這段在做的是探索、驗證、收斂與對齊。
例如：

* 需求其實要解的是哪個問題？
* 哪個流程才是專家的解題方式？
* 哪些假設成立、哪些不成立？
* 如果做成系統，行為邊界應該在哪裡？

### ② 執行確定性的任務

這段才是把事情做出來、做穩、做進產品，包括：

* 實作
* 測試
* 整合
* 部署
* 維運

而這兩段中間最關鍵的產物，就是：
**明確且可執行的 SPEC（規格）與 REQ（驗證要求）**。

AI 的影響在於，它讓第二段（確定性執行）的效率大幅提升，於是第一段（不確定性處理）的品質，會比以前更直接地決定整體成敗。

---

## 為什麼我開始用 Prototype 當作規格收斂的主戰場

過去我們很容易把規格（SPEC）想成一份文件，先寫完，再交給工程團隊實作。這做法當然不是不行，但在不確定性高的階段，常常會遇到同樣的問題：

* 寫得很完整，但其實描述不夠精準
* 異動很難維護
* 很難驗證規格是不是「真的可行」
* PO / RD / Architect 之間很難對焦

所以我現在比較傾向的做法是：

**先用 vibe coding 做 Prototype，拿 Prototype 去收斂需求與規格，再從 Prototype 萃取出高品質 SPEC。**

這裡的 Prototype，不只是 demo，而是比較接近「系統模型」的概念。它同時描述了：

* **行為**（因為可以直接 Run）
* **設計**（因為通常有 API spec、資料結構、schema）
* **整合**（因為可以模擬跨模組、跨系統互動）

換句話說，Prototype 在這裡不是拿來「做樣子」，而是拿來 **驗證設計與溝通規格**。

這其實就是我過去常講的抽象化系統建模，只是以前做這件事成本很高，很多團隊不願意投入太多人力在「最終不交付」的模型上。現在有 AI 和 Coding Agent，建模成本被壓低很多，架構師自己就能做出很高價值的模型，這件事 suddenly 變得很划算。

## Lite EC demo：我怎麼把這套方法落在實際開發

我最近在整理一個 demo code，題目是 EC 系統開發（我稱作 **Lite EC**），這個案例剛好很能說明我上面講的工作方法。

我把整個 PoC 切成幾個模組，並用箭頭表示開發順序（由左到右推進）。另外有一張對照圖，是同一張架構圖加上實際 .NET package name，方便直接對 source code。

這個案例裡，我刻意做了一件事：
**把我的角色放在「起點與終點」的把關，而不是中間每一行 code 的實作。**

### 我做的事情是什麼？

從左到右，我會親自 review：

* **SPEC（起點）**
* **REQ（終點，例如 unit test / request 驗證）**

而且不是 review 到概念層而已，我會把細節確認到 source code 等級，目標是確保：

* 規格起點足夠清楚
* 驗證終點足夠清楚
* 中間有足夠的約束條件讓 Coding Agent 持續推進

這樣一來，Coding Agent 就能在中間段（例如 core 開發）比較穩定地自主持續運作，直到完成我要求的部分。

### Lite EC 的模組思路（簡化說法）

你可以把它理解成幾個重複模式組合起來的結構：

* 左側是起點約束：`SPEC (interface)`、`REQ (unit test)`
* 中間是核心實作：`EC Core (SDK)`
* 上方是 API 合約與 request 行為驗證：`SPEC (OpenAPI)`、`REQ (CURL)`
* 右側是 API 對外服務：`EC Storefront API`
* 虛線部分是 UI：`UI SPEC`、`EC WebUI`（目前仍在構想，尚未納入這次實作）

這種設計對我來說很重要，因為它不是單純「切模組」，而是在設計一個讓 Agent 能工作的環境：

* 輸入清楚（規格）
* 完成條件清楚（測試 / request 驗證）
* 邊界清楚（模組接口）
* 順序清楚（箭頭代表依賴與推進節奏）

這時候架構師的高槓桿工作就不是「親手把 core 寫完」，而是：
**設計一個 Agent 可以持續產生正確產出的條件。**

## 這套方法不是取代 DevOps，而是拆成兩個更合理的循環

很多人看到 Prototype-driven 的做法，會直覺擔心一件事：
「這樣是不是只是在做 PoC？工程紀律呢？DevOps 呢？」

我的答案剛好相反：
**這不是跳過 DevOps，而是把風險拆開，讓不同目的的循環各自跑得更有效。**

我現在會把 AI 輔助開發拆成兩個循環：

> **我現在會把 AI 輔助開發拆成兩個循環：先用 Prototype 跑一個很小、很快的 BizDevOps 循環，先確認價值是否能被交付；價值確認之後，再進入以工程化與規模化為主的 DevOps 循環。**

也就是說，我不是想用 Prototype 取代後面的工程流程，而是先用它解掉前段的價值風險與需求風險，再把已經收斂的東西交給工程循環去放大。

進一步講，我對架構師角色的理解也跟著變了：

> **架構師的工作不再是直接把所有工程風險一次扛完，而是先用 Prototype 與 AI 工具快速消化價值風險，再把已經收斂的規格與驗證條件交給工程化的 DevOps 流程去放大。**

這個分工我覺得非常重要，因為它同時保住了兩件事：

1. **前段探索的速度**
2. **後段工程的紀律**

---

## Lite EC 放在雙循環裡，剛好是「小型 BizDevOps 循環 + 工程前置」

如果套回 Lite EC 這個案例，我會說它目前主要落在前段的 **BizDevOps 小循環**，但已經刻意加入很多工程前置的元素。

它做的不是把整個產品做完，而是先確認：

* 這個切法有沒有價值交付的可能
* 這個規格能不能被實作
* 這個 API 合約是否可行
* 這些驗證方式是否能穩定約束 Agent 的產出

所以在 Lite EC 裡，我才會把這些東西前置：

* `SPEC (interface)`
* `REQ (unit test)`
* `SPEC (OpenAPI)`
* `REQ (CURL examples)`

這些不是裝飾，它們本質上就是在定義：

* 「什麼叫做完成」
* 「什麼叫做符合預期」
* 「什麼叫做能往下一階段推進」

這也是為什麼我會說，這種做法不是讓 Agent「亂寫 code」，而是讓 Agent 在工程約束裡加速 delivery。

---

## 為什麼這比傳統「先寫文件再開發」更有效

這不是說文件不重要，而是說在不確定性高的階段，只靠文件很容易卡在幾個老問題。用 Prototype 作為規格前段工程，實際上會讓很多事變得更可控。

### 1) 規格異動難維護 → Prototype / code 比較容易維護一致性

如果規格已經透過 Prototype 落成部分 code 或模型，異動時可以利用重構工具與相依分析去做一致性調整，比純文件追相依可靠很多。

### 2) 規格異動難驗證 → 測試可以變成終點約束

像 Lite EC 這樣把 `REQ (unit test)` 放進起點設計，其實是在前置完成條件。規格一旦異動，不是只改描述，而是可以直接驗證這次異動是否仍符合系統要求。

### 3) 規格異動難溝通 → 可執行模型能讓跨角色對焦更快

PO、RD、Architect 討論的焦點會從抽象文字，轉成具體行為、操作流程與結果觀察。這對跨模組、跨團隊設計特別有幫助。

---

## 這其實是把軟體工程方法借力到 AI 工作流

有時候大家會把 AI 工作流講得很像在追新工具，但我實際做下來的感覺剛好相反：

我用的反而是很傳統、很紮實的軟體工程觀念，只是現在終於有 AI 幫忙，把它們落地得更頻繁、更划算。

例如：

* 規格（SPEC）
* 測試（REQ / Done Criteria）
* 抽象與模組化
* 可驗證性
* 重構與一致性維護
* API 合約與行為驗證

這些東西以前也都知道重要，但常常受限於時間與人力成本，做不到位。現在有 Coding Agent，架構師可以把精力集中在高槓桿決策點，讓 AI 去放大執行。

---

## 真正的變革不是「AI 幫我寫 code」，而是工作流程被重排了

如果只看表面，AI 帶來的變化好像是「寫 code 速度變快很多」。這當然是真的，但我覺得更深一層的變化是：

* 架構師與資深工程師的價值重心改變了
* 規格與驗證條件的重要性被放大了
* Prototype 不再只是 demo，而是收斂 SPEC 的系統模型
* 開發流程可以拆成「先驗價值、再做工程化」的雙循環

所以我現在回頭看 Kent Beck 那句話，還是覺得很準。
只是我自己的版本會更具體一點：

* 那 90% 沒有消失，只是市場價格下降了
* 剩下的 10% 之所以被放大，是因為 AI 能把你定義好的方法快速擴張
* 真正稀缺的，不再是你能寫多快，而是你能多快定義出「什麼是對的」

## 給架構師／資深工程師的幾個實作建議

如果你也在想 AI 時代自己該怎麼調整，我會建議先練這三件事（不一定是先追最新工具）：

### 1) 問題拆解與流程訪談

先搞清楚專家是怎麼解題的，哪些步驟 AI 做得到、哪些步驟還需要人。

### 2) 用 Prototype 建模，而不是只寫文件

讓需求、設計、驗證可以在可執行模型上快速收斂。

### 3) 設計驗證條件（Done Criteria）

把「完成」定義清楚，讓 Agent 的產出可以被穩定約束，而不是靠人工感覺判斷。

像 Lite EC 這類題目就很適合拿來練習，因為它同時有：

* 模組切分
* API 合約
* 測試約束
* 後續 UI 擴展空間

剛好可以練到「人把關起點與終點，中間交給 Agent 持續推進」的節奏。

## 結語

這篇先整理到這裡。對我來說，AI 帶來的最大變化不是「終於可以少寫 code」而已，而是：

**我開始更清楚地知道，自己該把時間花在哪裡，才能讓整個系統（和團隊）跑得更快、更穩。**

如果你也是在做架構、帶團隊，或正在摸索 AI 輔助開發的工作方法，我很推薦你試著從「雙循環」的角度重新看一次自己的流程：

* 前段先用 Prototype 跑小型 BizDevOps 循環，確認價值交付
* 後段再進入工程化與規模化的 DevOps 循環

這樣做不只不會犧牲工程品質，反而更有機會把風險拆開，讓每個環節都在更適合的節奏下運作。
