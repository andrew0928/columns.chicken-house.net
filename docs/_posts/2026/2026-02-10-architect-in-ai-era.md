從 AI 開始可以寫出漂亮的程式碼以來, 我一直在想這件事:

> 當 Coding Agent 已經能負責大部分的開發任務時，架構師真正該做的是什麼？

為了想清楚這件事, 我其實做過很多嘗試｡ 這次我把焦點擺在過去我最常做的 "架構設計" 類型的專案, 這種專案困難的地方是, 你必須精準的掌握系統未來發展的需求, 用正確的軟體架構來實作｡ 這想法延續到 2023, 當時我啟動了一個 side project: Headless Commerce, 這專案的目的只是為了 API Design Workshop 而準備的示範系統, 重點在 API 規格的設計與驗證, 而實作層面則省略了很多環節｡

這次, 我想要把過去這 side project 沒補完的實作先補齊, 然後把真正的應用案例 (難題) 套用上去, 我的目的是想嘗試看看, 過去開發人員需要具備高度抽象化思考能力才做的來的任務, 現在靠架構師 + AI 能完成到什麼程度? 有了 AI 的加持, 架構師的角色是否該做什麼改變? 哪些部分更有價值了? 哪些部分交給 AI 就行了?

# 0. 我的動機, 以及我想驗證的事


其實三年前 Kent Beck 就在 twitter 上面發表了這則推文 (也是我一直在想的問題), 談了類似的觀點:

```

The value of 90% of my skills just dropped to $0. The leverage for the remaining 10% went up 1000x. I need to recalibrate.

```

想了很久, 也嘗試了很多不同的做法, 直到完成了這個 side project 後, 寫了這篇文章｡ 我想用實際的執行案例, 來驗證哪些範圍是 10% 的部分? 這 10% 的技能, 我該做什麼才能讓價值變成 1000x ? 對結果有興趣的可以繼續往下看, 我會從這個案例, 提供這些過程的記錄, 來驗證我的想法｡

只要能找到有代表性的 "難題", 並且把他完成, 我就能從這過程中確認我的想法｡ 這難題不能是單純的 "原本需要很多人力" 需求的難題, 而是需要搭配巧妙地結構設計類型的難題｡ 回顧過去, 我做過最多類型的 "練習", 就屬交易相關的應用了, 我挑了 2023 這個專案, 這專案已經有很明確的核心流程, 但是還沒具備擴充能力｡ 這次我想驗證核心流程 (cart / checkout) 能否在不被破壞的前提下, 透過正確的擴充機制設計, 定義明確的邊界與驗證機制, 讓 AI 能有效率的自主完成任務? 

因此, 我假想了可能的業務需求:

> 我希望有一套具備高度擴充能力的 e-commerce system, 能夠處理最核心的交易行為 (購物車 + 結帳), 這部份需要穩定可靠, 不適合頻繁變更｡
>  
> 但是交易相關的商業邏輯, 我希望能有高度客製化能力的擴充機制 (例如: 擴充套件 / extension), 我希望能擴充 (未來) 客戶專主的 "可被販賣的服務" 類型, 也要能擴充 "折扣計算的規則"


"高度擴充能力" 這句話可大可小, 我挑了兩個身邊就能觀察到的實際案例:

1. 跨多系統整合的優惠活動 - Apple BTS 教育方案的實作
2. 在標準的結帳流程, 處理服務 (非商品) 的販售 - Andrew PetShop 線上預約寵物美容服務

這考驗了主系統對 "擴充機制" 這件事的準備與應變能力有多充分, 經驗跟難度是有的, 沒經驗的人可能連規格都開不出來, 看起來是個有鑑別度的題目｡ 這題目能表達出複雜度的考量, 而不是只有工作量或是產能的考量, 而對我 (架構師) 而言, 先把系統的體質 (品質) 做到位了, 再來談效率 (加速, 成本) 才有意義｡

從工程的角度來看, 這兩個需求困難點在於:

> 新需求通常都是再主系統完成 (並且上線後) 才開始陸陸續續浮現出來的, 系統必須在那之前就定義好哪些範圍需要有擴充機制的設計

因此, 你沒有機會看到需求才來設計架構｡ 如果每次都是看到需求再改架構的話, 那架構設計就會退化成一次一次的 "客製化" 了... 所以你只有先規劃好整體架構, 定義能擴充的範圍與邊界, 然後面對這些需求時, 才能有有系統且安全 (重要的是已被驗證過) 的解決方式｡

因此, 關鍵是: 順序跟範圍的判斷｡ 你是先準備好擴充機制? 還是先面對需求? 先準備好擴充機制會不會過度設計 (做了結果用不到, 徒增複雜度)? 這些決策衍生出來的開發規格, 其實需要高度仰賴開發團隊的能力水準才能做的到｡ 而具備這些能力水準的人力, 往往就變成主要的瓶頸｡ 因此, 我期待 AI 能優先解決的是這種 "能力" 的問題, 再來看 "效率" 跟 "成本" 是否能跟上｡

如果成功的話, 架構師可以解放團隊的開發能力, 可以真正改善 "品質" 的部分｡ 品質提高了, 加速才開始變的有意義 (有價值)｡ 我想 Kent Beck 那段話背後的意義就是這樣吧｡

# 1. 重構

接下來, 我會分幾個段落進行, 過程中我會記錄我跟 AI 的協作方式, 這是我自己覺得有效率的實踐方式, 也是我想分享的做法:

1. 先補完主系統的擴充能力 (商品, 折扣)
2. 模擬實作 Apple Store (BTS)
3. 模擬實作 Andrew PetShop (預約服務)


首先要面對的就是, 當年 (2023) 我只定義了 API Spec, 實作都未完成, 我先逐步把這些構想定義清楚, 讓 AI 幫我補完這些實作



# 1. 選題: AndrewShop

這次我挑選的題目，是我在 2023 年寫的 AndrewShop。當時為了談 API contract design，因此我只開發了 Headless Mode，只有 API，沒有 UI 的參考設計；而 API 背後的實作也大量簡化，不重要的環節我甚至根本沒寫就直接帶過去了。

這份 source code，後來被我拿來闡述 API design，也拿來延伸做對談式購物「安得魯小舖」，都是靠這個 side project 完成的。

這次我想驗證的是：

> AI coding 能否升任「包含複雜架構設計」相關的功能開發、維護、重構任務？

因此我刻意挑了一個困難的目標：  
我希望這個服務，能把商業邏輯設計成像擴充套件一樣來處理。客戶可以高度自訂販售的商品（例如非實體商品、預約服務等等），同時也能高度擴充折扣規則（甚至可以自己寫 code 定義折扣計算邏輯）；而這些設計，又都能在既有的購物車內完成結帳。

結帳本身其實很複雜，但是流程固定，需要高度精確跟可靠，不希望被隨意調整。  
所以這次的真正挑戰不是「多做幾個功能」，而是：

> 能不能在不破壞核心結帳流程的前提下，讓商品型態與優惠規則都具備高度擴充性？

# 2. 刻意練習: 兩個難題

所以我想像了兩個案例，希望兩個完全不同屬性的客戶，都能用同一套系統來服務。

我示範了兩個客戶需求：

## 2.1 Apple Store

每年都有 BTS 教育優惠，關鍵是：

- 消費者通過 email 認證，確認符合大專教職員或學生身分，並且有優惠數量限制
- BTS 專案的優惠規則（例如：MacBook + AirPods、iPad + Apple Pencil 等等）

## 2.2 Andrew PetShop

除了販售寵物商品之外，也能一起預約寵物美容服務，能一起結帳，並且有優惠方案：

- 預約需求必須跟商品一樣，要能「放入」購物車內結帳
- 預約有時段跟指名服務人員的要求，有時間、場地跟人數限制
- 預約服務 + 指定商品要有綜合優惠

其實這些是我故意安排的「難題」。

如果沒有好好控制內部架構設計，你很可能在碰到第三個客戶時就卡關。而架構師扮演的角色，本來就是做好這種設計；我真正好奇的是：

> 架構師能夠怎樣跟 AI 協作，來完成這種層級的任務？

# 3. 我想驗證: 我該怎麼帶 AI 做?

最後衍伸出來，其實都是幾個很基礎的實踐，只是要確實做到位而已。  
這些做法，過去我都各別在 Facebook 聊過；這次我想把它們整理在一起，讓大家能清楚看到我思路的全貌。

理想的 AI Native Workflow，我認為至少要思考這幾件事：

## 3.1 用 AI 找出該做的事情：決定規格（做對的事）

規格很重要，尤其是要包含核心系統的切分與邊界設計。  
這部分值得你花一些 token 來打造 prototype，快速驗證這需求與規格是否值得開發。

## 3.2 用 AI 有效率地完成任務：照規格開發（把事做好）

想像把 AI 當外包團隊。  
你要有效率地外包，就必須給對規格，並且預先設計好對你自己方便且有效的驗收方式。剩下的就讓 AI 努力幹活，能通過驗收方式之後再回報給你。

## 3.3 有效管理 AI 團隊：定義邊界，按照計畫進行（掌控方向）

如果專案規模很大，就要切成多個「外包」專案。  
而正確的切割，仰賴你拿捏各個子系統的邊界定在哪裡、介面該怎麼設計；同時你還要能有效管理整個開發計畫，有序地逐步完成目標。

不要最後變成每個外包專案都成功了，但整體使命沒有完成。

## 3.4 刻意練習，隨時維持自己掌控 AI 的能力（學習成長）

AI 進步神速，你必須跟上，才有辦法管理 AI 團隊。  
這些經驗與知識，沒有人能完整教你；你得自己掌握在這個時代的做事與學習方法。

這四個環節，是我過去一年累積下來的心得。  
把它們擺在一起看，你才會理解它們的全貌。

我面對這個 side project 的時候，其實就是不斷重新組合這四個招式，最後才完成整個任務。

# 4. 實際執行的案例

我的做法是：

1. 把整個專案切成好幾個步驟（plan mode，輸出 roadmap），從全貌來檢視，確認每個步驟（phase）都在逐步往目標靠近
2. 每個步驟（phase）都應該有明確的邊界；跨越邊界的部分都該有明確定義。我的做法是用 code 把每個 phase 該完成的部分訂出 contract 當作起點，而這份 contract 若被正確實作，就應該能通過對 contract 所寫的 test 當作終點。定義完成後，就讓 agent 開發到好為止，最後再由我人工檢視做最後確認
3. 檢視的過程中，務必確認我認同 AI 的決策才能放行。若碰到我不熟悉的領域、無法決定，就多花一些 token，讓 AI 產生對應的說明、文件、圖表等資訊，協助我確實理解狀況，直到能做出讓我安心的決策為止

我背後的想法是：

身為架構師，我終究該對系統的全貌有所掌握，因此我會主導整個開發計畫的進行，因為我要為它的成敗負責。  
而我熟悉 coding agent 的運作模式，因此我知道細節要整理到什麼程度後，才能放心交給 agent 去處理。

只要能讓 agent 形成能夠自我驗證的 loop，這件事就算完成了八成。  
這時我需要做的，反而是 review contract（code）、review test（code），以及觀察 agent 最終交付的成果，做最後確認。

# 5. 這次案例的 Roadmap 規劃

回到這個案例，我大致這樣切分。  
Phase 0 是起點，也就是 2023 當年做完的狀態。

這次的目標是：

> 用正確的系統架構，完成能同時適用 Apple Store / Andrew PetShop 的系統開發

"三年後的架構師應該做什麼?"

其實從 AI 開始改變開發人員的工作方法之後, 我一直都在想這件事, 直到最近, 我翻新了 2023 年為了展示 e-commerce api design 的範例, 模擬大型系統怎麼靠 AI 來進行翻新, 以及持續改進, 增加新功能並且持續迭代的工作流程. 這個 side project 從構思到完成, 大約花了 2 週 (其實大部分都是在思考做法, 真正執行大約花了三個晚上)

這篇文章, 我想記錄一下我的執行過程, 搭配我背後為何這樣執行的想法. 現在的社群狀況是資訊過多 (大部分都是 AI 生成的), 然而有參考價值的內容太少, 因此我決定搭配執行的成果, 來論述這些想法. 雖是我主觀的看法, 不過搭配實際案例, 大家其實可以參考我的做法, 擷取對你們有價值的部分即可｡

# 0, 寫這篇文章的動機

這次我挑選的題目, 是我在 2023 年寫的 AndrewShop, 當時為了談 API contract design, 因此我只有開發 Headless Mode, 只有 API, 沒有 UI 的參考設計, 而 API 背後的實作也大量簡化, 不重要的環節我就根本沒寫就帶過去了, 這份 source code, 是我拿來闡述 API design, 以及後來的對談式購物 - 安得魯小舖, 都是靠這個 side project 完成的.

這次我想驗證的是: AI coding 能否升任 "包含複雜架構設計" 相關的功能開發 / 維護 / 重構的任務要求? 因此我挑了困難的目標, 我希望這服務, 能將商業邏輯像擴充套件一樣的處理｡ 客戶可以高度自訂販售的商品 (例如: 非實體商品, 預約服務等等), 同時也能高度擴充折扣規則 (可以自己寫 code 定義折扣計算邏輯), 而這些設計, 都能在既有的購物車內完成結帳 (結帳很複雜, 但是流程固定, 需要高度精確跟可靠, 不希望能隨便調整)｡

所以我想像了兩個案例, 希望兩個完全不同屬性的客戶, 都能用同一套系統來服務｡ 我示範了兩個客戶需求:

1. Apple Store, 每年都有 BTS 教育優惠, 關鍵是:
- 消費者通過 email 認證, 確認符合大專教職員或是學生身分, 並且有優惠數量限制
- BTS 專案的優惠規則 (例如: MacBook + AirPods, iPad + Apple Pencil 等等)

2. Andrew PetShop, 除了販售寵物商品之外, 也能一起預約寵物美容服務, 能一起結帳, 並且有優惠方案
- 預約需求必須跟商品一樣, 要能 "放入" 購物車內結帳
- 預約有時段跟指名服務人員的要求, 有時間, 場地跟人數的限制
- 預約服務 + 指定商品要有綜合優惠

其實這些是故意安排的 "難題", 沒有好好的控制內部架構設計的話, 你會在碰到第三個客戶就卡關, 而架構師扮演的角色就是做好設計, 而我好奇的是, 架構師能夠怎樣跟 AI 協作來完成這種層級的任務?

最後衍伸出來, 其實都是幾個很基礎的實踐, 只是要確實做到位而已｡ 這些做法過去我都各別在 Facebook 聊過, 我把他整理在一起, 讓大家能清楚的看清我思路的全貌. 理想的 AI Native Workflow, 應該要思考這幾件事:


1. 用 AI 找出該做的事情 - 決定規格 (做對的事):  
規格很重要, 尤其是要包含核心系統的切分與邊界設計｡ 這部份值得你花一些 token 來打造 Prototype 快速驗證這需求與規格是否值得開發。

2. 用 AI 有效率地完成任務 - 照規格開發 (把事做好):  
想像把 AI 當外包團隊, 你要有效率的外包, 給對的規格, 並且預先設計好對你自己方便且有效的驗收方式, 剩下的就讓 AI 努力幹活, 能通過驗收方式後再回報給你。

3. 有效的管理 AI 團隊 - 定義邊界, 按照計畫進行 (掌控方向):
如果專案規模很大, 切成多個 "外包" 專案, 而正確的 "切割" 就要仰賴你拿捏各個子系統的邊界定在哪裡, 介面該怎麼設計; 而你要能有效的管理整個開發計畫, 有序的逐步完成目標 (不要每個外包專案都成功, 但是你的使命沒有完成)

4. 刻意練習, 隨時維持自己掌控 AI 的能力 (學習成長):
AI 進步神速, 你必須要能跟上才有辦法管理 AI 團隊, 這些經驗與知識沒人可以教你, 你要掌握在這時代的做事與學習方法


這四個環節, 是我過去一年累積下來的心得, 擺在一起看你才能理解他們的全貌｡ 我面對這個 side project 的時候, 其實就是不斷的重新組合這四個招式, 就完成整個任務了｡

我的做法是:

1. 把整個專案切成好幾個步驟 (plan mode, 輸出 roadmap), 從全貌來看檢視, 確認每個步驟 (phase) 都有逐步往目標靠近
2. 每個步驟 (phase) 都應該要有明確的邊界, 跨越邊界的部分都該有明確的定義. 我的做法是用 code 把每個 phase 該開發完成的部分訂定 contract 作為起點, 而這份 contract 若實作完成則應該通過對 contract 寫的 test 當作終點, 定義完成後就讓 agent 開發倒好為止, 讓我人工檢視做最後確認
3. 檢視的過程中 "務必" 確認我認同 AI 的決策才能放行｡ 若碰到我不熟悉的領域無法決定, 就多花一些 token, 讓 AI 產生對應的說明, 文件, 圖表等等資訊, 協助我確實理解狀況, 直到能做出令我安心的決策為止

我背後的想法是:

身為架構師, 我終究該隊系統的全貌有所掌握, 因此我會主導整個開發計畫的進行 (因為我要為他的成敗負責), 而我熟悉 coding agent 的運作模式, 因此我知道我把細節收整到什麼程度後, 能放心的交給 agent 去處理 (只要能讓 agent 形成能夠自我驗證的 Relph-Loop 就算完成了八成了), 這時我需要的就是 review contract (code), 跟 review test (code), 以及觀察 agent 最終交付的成果做最後確認

回到這個案例, 我大致這樣切分 (phase 0 是起點, 就是 2023 當年做完的狀態), 以下就是我這次的 Roadmap:

目標: 用正確的系統架構, 完成能同時適用 Apple Store / Andrew PetShop 的系統開發

Roadmap:

1. Phase1 - 重構, 切出 Discount / Product 領域物件, 並且追加 Shop 層級的啟動設定
我先不改變整套系統的運作, 只做架構重構的調整. 我知道這次任務的挑戰, 因此先做好 Discount / Product 兩個 Domain 的設計切割. 過去沒有確實做好的部分趁這次補上, 有了 AI 的幫助, 這部份如虎添翼, 大概花費 4 ~ 6 hr 就完成了

2. Phase2 - 重構, 切出 Checkout 領域物件

3. Phase3 - 修正, 確保整體系統能正常運作 ( API, Console UI, Web UI )

4. Phase4 - 實作 Apple Store

5. Phase5 - 實作 Andrew PetShop

ai 寫 code 越來越厲害, 整個軟體開發產業不可能再用一樣的方法來 "生產" 軟體跟服務了｡ 兩年前我還看不準這變化會有多劇烈, 未來我 (架構師) 的角色該做什麼? 現在看出一些端倪了, 我把我的想法, 以及我自己用 side project 驗證的結果整理成這篇文章, 來印證我自己對未來的想像

我從三年前我看到 Kent Beck 講了這句話, 就一直在思考這問題:

> “The value of 90% of my skills just dropped to $0. The leverage for the remaining 10% went up 1000x. I need to recalibrate.”

翻成白話大概是：

> AI 讓我 90% 的技能價值快速下降，但剩下 10% 的價值被放大了 1000 倍，所以我必須重新校準。

對我的角色 (架構師) 而言, 90% 是什麼? 剩下的 10% 是什麼? 我該做什麼改變 (重新校準)? 還好過去有一點管理的經驗, 大致上該做的是:

1. 調整流程, 90% 的部分盡快用其他方式替代, 轉移給其他人 (角色 + AI), 或是直接交給 AI 執行
2. 調整工作方法, 讓自己盡可能的放大花在 10% 上的時間
3. 通常 10% 的任務要能佔滿, 可能外部流程也需要調整 (不然可能沒那麼多案子需要找你)
4. 這些調整通常也會改變人力配比, 更長期來看人力配置也需要改變

總之, 從最後的結果來看, 如果你的 10% 能力是不可取代的, 限制理論也提到這觀念, 如果優化之後你已經變成整個流程的瓶頸 (大家都再等待你發揮這 10% 技能的時候, 不是指你擺爛所以影響到大家的那種瓶頸), 你就算成功的調整定位了｡ 舉個大家都知道的例子, 全世界的晶片都必須仰賴戶國神山的產能, 整個供應鏈會調節成讓戶國神山發揮最大產能 (他是瓶頸) , 就代表你的價值已經被放大到極限了


原則講完了, 接下來我就拿我實際的案例, 來談談我對未來架構師角色的想法吧, 因為談的是整個開發流程, 因此其他角色的改變我也會一起看, 只是是從架構師的視角來看這整個改變而已｡

我粗略的拆幾個階段,有幾個片段的觀察, 是確定的:

需求 -> (分析) -> 規格 -> (設計) -> (開發) -> 軟體

括號裡的是 "動詞", 代表要有人去處理的任務, 沒有刮起來的是 "名詞", 代表資訊, 文件, 或是產出｡ 這幾個階段的執行方式跟角色, 我的觀察是:

1. (設計) 是要從確認的規格, 推導出解決問題的主要結構, 過去大概是 SA/SD 的 SD 階段, 如果 context 明確的話, 這部份應該 ai 能處理掉 90% 沒問題, 剩下只是策略上的選擇, 或是無法明確化的部分需要人來處理｡ 這階段 "選擇" 會比 "設計" 重要, 因為他更難以意料

2. (開發) 是從規格以及設計完成的解題架構, 把他落實成真正能運行的程式碼, 這段過程講求的是勞動力的投入, 以及大量的紀律要求, 說實在話這段讓 AI 來做完全沒懸念, 不用等到未來, 只要前面階段有做確實, 現在可以說 100% 給 AI 沒問題了

3. (分析) 則難講, 難的地方在於需求不一定能講的清楚, 領域知識也不斷的在變化, AI 必須要有足夠且正確的 context 給他, 產出的品質才能控制, 這些需要了解狀況的人來做決策, 溝通, 驗證, 甚至依靠產業經驗培養出來的 "直覺" 來決定的過程, 也就是大家常說的 "品味", 都屬於這類, AI 能分攤多少我比較保守, 40% 左右





# 當 Coding Agent 能寫 code，架構師的價值就從「實作產出」轉向「規格收斂、驗證條件與系統建模」

前幾天聊 Agent MVP 做法時，我心裡真正想談的其實不是「某個工具好不好用」，而是另一個更根本的問題：

**AI 的進步，工作流程應該要有根本上的改變才對。那麼架構師（或資深技術人員）本身該做什麼調整？**

這幾年很多人會引用 Kent Beck 那句話：

> “The value of 90% of my skills just dropped to $0. The leverage for the remaining 10% went up 1000x. I need to recalibrate.”

翻成白話大概是：

> AI 讓我 90% 的技能價值快速下降，但剩下 10% 的價值被放大了 1000 倍，所以我必須重新校準。

這句話我一直覺得很有道理，但如果你沒有真的弄清楚那個 **10% 到底是什麼**，也沒有真的調整自己的工作方法，那它就很容易只剩下心靈雞湯。

我這篇想談的，就是我這段時間實作下來的一個答案：
**AI 時代，架構師的價值更集中在處理不確定性、收斂規格、設計驗證條件、建立系統模型，以及定義讓 Agent 能持續運作的條件。**

---

## 架構師的 10%，其實是「主動成為瓶頸」

如果用限制理論（Theory of Constraints）的角度來看，整個系統效率取決於瓶頸。換句話說，當 AI 大量接手可被標準化、可被加速的工程工作時，對架構師而言，真正高價值的做法反而是：

**主動讓自己成為那個關鍵瓶頸。**

這裡說的「瓶頸」不是拖慢團隊，而是你把時間和精力集中在那些 **非你不可**、而且會影響整體結果的環節。這些通常不是「多寫幾千行 code」，而是：

* 問題拆解與建模
* 需求與規格收斂
* 驗證條件設計（Done Criteria）
* 模組邊界與跨系統介面定義
* 跨團隊溝通與風險前置消化

我後來重新回頭看這兩年 AI 對軟體開發的改變，越來越確定：
**AI 強的是加速「確定性任務」，而人的價值會更集中在處理「不確定性」。**

## 架構師的核心任務沒有變，但工作方法變了

我對架構師工作的理解一直沒有變太多：本質上還是要理解商業需求與技術要求，替產品與決策者翻譯需求，再把它轉成開發團隊能執行的做法（規格）。

但在 AI 時代，我會把整個流程更明確地拆成兩段：

### ① 處理不確定性的問題

這段在做的是探索、驗證、收斂與對齊。
例如：

* 需求其實要解的是哪個問題？
* 哪個流程才是專家的解題方式？
* 哪些假設成立、哪些不成立？
* 如果做成系統，行為邊界應該在哪裡？

### ② 執行確定性的任務

這段才是把事情做出來、做穩、做進產品，包括：

* 實作
* 測試
* 整合
* 部署
* 維運

而這兩段中間最關鍵的產物，就是：
**明確且可執行的 SPEC（規格）與 REQ（驗證要求）**。

AI 的影響在於，它讓第二段（確定性執行）的效率大幅提升，於是第一段（不確定性處理）的品質，會比以前更直接地決定整體成敗。

## 為什麼我開始用 Prototype 當作規格收斂的主戰場

過去我們很容易把規格（SPEC）想成一份文件，先寫完，再交給工程團隊實作。這做法當然不是不行，但在不確定性高的階段，常常會遇到同樣的問題：

* 寫得很完整，但其實描述不夠精準
* 異動很難維護
* 很難驗證規格是不是「真的可行」
* PO / RD / Architect 之間很難對焦

所以我現在比較傾向的做法是：

**先用 vibe coding 做 Prototype，拿 Prototype 去收斂需求與規格，再從 Prototype 萃取出高品質 SPEC。**

這裡的 Prototype，不只是 demo，而是比較接近「系統模型」的概念。它同時描述了：

* **行為**（因為可以直接 Run）
* **設計**（因為通常有 API spec、資料結構、schema）
* **整合**（因為可以模擬跨模組、跨系統互動）

換句話說，Prototype 在這裡不是拿來「做樣子」，而是拿來 **驗證設計與溝通規格**。

這其實就是我過去常講的抽象化系統建模，只是以前做這件事成本很高，很多團隊不願意投入太多人力在「最終不交付」的模型上。現在有 AI 和 Coding Agent，建模成本被壓低很多，架構師自己就能做出很高價值的模型，這件事 suddenly 變得很划算。

## Lite EC demo：我怎麼把這套方法落在實際開發

我最近在整理一個 demo code，題目是 EC 系統開發（我稱作 **Lite EC**），這個案例剛好很能說明我上面講的工作方法。

我把整個 PoC 切成幾個模組，並用箭頭表示開發順序（由左到右推進）。另外有一張對照圖，是同一張架構圖加上實際 .NET package name，方便直接對 source code。

這個案例裡，我刻意做了一件事：
**把我的角色放在「起點與終點」的把關，而不是中間每一行 code 的實作。**

### 我做的事情是什麼？

從左到右，我會親自 review：

* **SPEC（起點）**
* **REQ（終點，例如 unit test / request 驗證）**

而且不是 review 到概念層而已，我會把細節確認到 source code 等級，目標是確保：

* 規格起點足夠清楚
* 驗證終點足夠清楚
* 中間有足夠的約束條件讓 Coding Agent 持續推進

這樣一來，Coding Agent 就能在中間段（例如 core 開發）比較穩定地自主持續運作，直到完成我要求的部分。

### Lite EC 的模組思路（簡化說法）

你可以把它理解成幾個重複模式組合起來的結構：

* 左側是起點約束：`SPEC (interface)`、`REQ (unit test)`
* 中間是核心實作：`EC Core (SDK)`
* 上方是 API 合約與 request 行為驗證：`SPEC (OpenAPI)`、`REQ (CURL)`
* 右側是 API 對外服務：`EC Storefront API`
* 虛線部分是 UI：`UI SPEC`、`EC WebUI`（目前仍在構想，尚未納入這次實作）

這種設計對我來說很重要，因為它不是單純「切模組」，而是在設計一個讓 Agent 能工作的環境：

* 輸入清楚（規格）
* 完成條件清楚（測試 / request 驗證）
* 邊界清楚（模組接口）
* 順序清楚（箭頭代表依賴與推進節奏）

這時候架構師的高槓桿工作就不是「親手把 core 寫完」，而是：
**設計一個 Agent 可以持續產生正確產出的條件。**

## 這套方法不是取代 DevOps，而是拆成兩個更合理的循環

很多人看到 Prototype-driven 的做法，會直覺擔心一件事：
「這樣是不是只是在做 PoC？工程紀律呢？DevOps 呢？」

我的答案剛好相反：
**這不是跳過 DevOps，而是把風險拆開，讓不同目的的循環各自跑得更有效。**

我現在會把 AI 輔助開發拆成兩個循環：

> **我現在會把 AI 輔助開發拆成兩個循環：先用 Prototype 跑一個很小、很快的 BizDevOps 循環，先確認價值是否能被交付；價值確認之後，再進入以工程化與規模化為主的 DevOps 循環。**

也就是說，我不是想用 Prototype 取代後面的工程流程，而是先用它解掉前段的價值風險與需求風險，再把已經收斂的東西交給工程循環去放大。

進一步講，我對架構師角色的理解也跟著變了：

> **架構師的工作不再是直接把所有工程風險一次扛完，而是先用 Prototype 與 AI 工具快速消化價值風險，再把已經收斂的規格與驗證條件交給工程化的 DevOps 流程去放大。**

這個分工我覺得非常重要，因為它同時保住了兩件事：

1. **前段探索的速度**
2. **後段工程的紀律**

## Lite EC 放在雙循環裡，剛好是「小型 BizDevOps 循環 + 工程前置」

如果套回 Lite EC 這個案例，我會說它目前主要落在前段的 **BizDevOps 小循環**，但已經刻意加入很多工程前置的元素。

它做的不是把整個產品做完，而是先確認：

* 這個切法有沒有價值交付的可能
* 這個規格能不能被實作
* 這個 API 合約是否可行
* 這些驗證方式是否能穩定約束 Agent 的產出

所以在 Lite EC 裡，我才會把這些東西前置：

* `SPEC (interface)`
* `REQ (unit test)`
* `SPEC (OpenAPI)`
* `REQ (CURL examples)`

這些不是裝飾，它們本質上就是在定義：

* 「什麼叫做完成」
* 「什麼叫做符合預期」
* 「什麼叫做能往下一階段推進」

這也是為什麼我會說，這種做法不是讓 Agent「亂寫 code」，而是讓 Agent 在工程約束裡加速 delivery。

---

## 為什麼這比傳統「先寫文件再開發」更有效

這不是說文件不重要，而是說在不確定性高的階段，只靠文件很容易卡在幾個老問題。用 Prototype 作為規格前段工程，實際上會讓很多事變得更可控。

### 1) 規格異動難維護 → Prototype / code 比較容易維護一致性

如果規格已經透過 Prototype 落成部分 code 或模型，異動時可以利用重構工具與相依分析去做一致性調整，比純文件追相依可靠很多。

### 2) 規格異動難驗證 → 測試可以變成終點約束

像 Lite EC 這樣把 `REQ (unit test)` 放進起點設計，其實是在前置完成條件。規格一旦異動，不是只改描述，而是可以直接驗證這次異動是否仍符合系統要求。

### 3) 規格異動難溝通 → 可執行模型能讓跨角色對焦更快

PO、RD、Architect 討論的焦點會從抽象文字，轉成具體行為、操作流程與結果觀察。這對跨模組、跨團隊設計特別有幫助。

## 這其實是把軟體工程方法借力到 AI 工作流

有時候大家會把 AI 工作流講得很像在追新工具，但我實際做下來的感覺剛好相反：

我用的反而是很傳統、很紮實的軟體工程觀念，只是現在終於有 AI 幫忙，把它們落地得更頻繁、更划算。

例如：

* 規格（SPEC）
* 測試（REQ / Done Criteria）
* 抽象與模組化
* 可驗證性
* 重構與一致性維護
* API 合約與行為驗證

這些東西以前也都知道重要，但常常受限於時間與人力成本，做不到位。現在有 Coding Agent，架構師可以把精力集中在高槓桿決策點，讓 AI 去放大執行。

## 真正的變革不是「AI 幫我寫 code」，而是工作流程被重排了

如果只看表面，AI 帶來的變化好像是「寫 code 速度變快很多」。這當然是真的，但我覺得更深一層的變化是：

* 架構師與資深工程師的價值重心改變了
* 規格與驗證條件的重要性被放大了
* Prototype 不再只是 demo，而是收斂 SPEC 的系統模型
* 開發流程可以拆成「先驗價值、再做工程化」的雙循環

所以我現在回頭看 Kent Beck 那句話，還是覺得很準。
只是我自己的版本會更具體一點：

* 那 90% 沒有消失，只是市場價格下降了
* 剩下的 10% 之所以被放大，是因為 AI 能把你定義好的方法快速擴張
* 真正稀缺的，不再是你能寫多快，而是你能多快定義出「什麼是對的」

## 給架構師／資深工程師的幾個實作建議

如果你也在想 AI 時代自己該怎麼調整，我會建議先練這三件事（不一定是先追最新工具）：

### 1) 問題拆解與流程訪談

先搞清楚專家是怎麼解題的，哪些步驟 AI 做得到、哪些步驟還需要人。

### 2) 用 Prototype 建模，而不是只寫文件

讓需求、設計、驗證可以在可執行模型上快速收斂。

### 3) 設計驗證條件（Done Criteria）

把「完成」定義清楚，讓 Agent 的產出可以被穩定約束，而不是靠人工感覺判斷。

像 Lite EC 這類題目就很適合拿來練習，因為它同時有：

* 模組切分
* API 合約
* 測試約束
* 後續 UI 擴展空間

剛好可以練到「人把關起點與終點，中間交給 Agent 持續推進」的節奏。
